# Список PR, требующих ревью

## Цель
Добавить HTTP-эндпоинт и вспомогательный метод, возвращающие открытые PR, которым ещё нужно ревью. Исключаются PR, которые недавно проверяли и в которых после ревью не было изменений.

## Затронутые файлы
- `TelegramWebhookBot.py` — добавить маршрут `/prs-to-review`, методы получения списка и проверки свежести ревью/изменений.
- `vercel.json` — изменения не обязательны (маршруты уже catch-all).
- `README.md` — по желанию документировать эндпоинт.

## Дизайн
- Добавить `GET /prs-to-review`, который запускает отправку сообщения в Telegram и возвращает JSON-статус (`{"status":"success"}`).
- Переиспользовать `_gitea_list_open_prs`, `_gitea_get_pr_reviews`.
- Для каждого открытого PR:
  - Получить ревью.
  - Определить последнее ревью с состояниями `approved`, `changes_requested`, `rejected`, `commented`, `request_changes` и его `commit_id`/`submitted_at`.
  - Сравнить `commit_id` последнего ревью с текущим `head.sha` PR (или использовать `updated_at <= submitted_at`, если SHA недоступен).
  - Пропустить PR, если последнее ревью есть и его `commit_id` совпадает с текущим head SHA (или PR не менялся после ревью).
  - Иначе включить PR в сообщение.
  - Пропускать PR без запрошенных ревьюеров (как в логике напоминаний).
- Сообщение формировать списком: репозиторий, номер, кликабельная ссылка на PR, автор, запрошенные ревьюеры. Если список пуст — отправить краткий статус «Нет PR, требующих проверки».

## Граничные случаи
- Нет ответа API ревью -> считать PR требующим ревью.
- Ошибка парсинга дат -> включать PR (fail open) и логировать warning.
- `GITEA_REPOSITORIES=ALL` -> разрешать через `_gitea_list_all_repos`.
- Дубликаты репозиториев устранять.

## Проверка
- `python -m py_compile TelegramWebhookBot.py`
- Ручной `GET /prs-to-review` при настроенных env возвращает JSON-список.
- Проверка логики: PR с ревью новее изменения исключается; PR, изменённый после ревью, включается.
